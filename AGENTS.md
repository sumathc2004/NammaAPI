# NammaAPI — project guide

`next dev` only rewrites the block above, between its markers. Everything below is maintained by hand; keep it accurate when the code changes.

## What this project is

Marketing website for **NammaAPI**, a business payments API platform for Indian businesses (payouts, payment collection, salary & bulk payments, payment automation), plus a **prototype phone + OTP login** backed by an external AEPS API.

- Next.js 16 (App Router, Turbopack), React 19, TypeScript (strict), Tailwind CSS v4.
- Every page is statically prerendered. The only dynamic routes are the API routes under `app/api/`.
- No database. The contact form emails via Resend; login calls the external AEPS API.

## Conventions

**Rendering**
- Server Components by default. Add `"use client"` only for interactivity. Current client components: `Header`, `ChatWidget`, `CodeTabs`, `FormInput`, the contact/signup/login forms, `OtpDialog`, `DashboardShell`, `DashboardSidebar`, `ProfileMenu`, and the error boundaries.
- Page chrome comes from layouts, not the root layout: public pages live in `app/(site)/` (website navbar and footer), the login page in `app/(auth)/` (no chrome), logged-in pages in `app/dashboard/` (dashboard shell). A new public page goes in `app/(site)/`. `app/not-found.tsx` renders outside all of them, so it adds `Header`/`Footer` itself.
- Keep pages static. Request-time APIs (`cookies()`, `headers()`, `searchParams`) in a page or layout make it dynamic.
- Error boundaries receive `retry` (Next 16), not `reset`.

**Content and data**
- Page copy lives in `lib/data/*.ts` and is rendered by components. Add products, industries or nav links there, not inline in JSX.
- Form option lists (business types, volumes, services) live in `lib/data/leadOptions.ts` and are shared by forms and server validation.

**Metadata and SEO**
- Every page exports `metadata = buildMetadata({ title, description, path })`. It appends `| NammaAPI`, sets the canonical URL and the shared Open Graph/Twitter image. Use `—`, not `|`, inside titles.
- Pass `noIndex: true` for pages that shouldn't be indexed (login, signup, dashboard), and keep them out of `app/sitemap.ts`.

**Styling**
- Use the theme tokens in `app/globals.css` (`brand-primary`, `brand-navy`, `text-secondary`, ...). `status-*` colors are only for transaction/status UI.
- Join classes with `cn()` from `lib/cn.ts`; it runs tailwind-merge, so a `className` passed to a component overrides its defaults.
- Animations are defined in `@theme` in `app/globals.css`; a global `prefers-reduced-motion` rule disables them.

**Forms and validation**
- Use `FormInput` / `FormSelect` / `FormTextarea`: they render the label, the required marker, and error/hint text wired up with `aria-describedby`.
- Validate with the shared functions in `lib/validation/` on both the client (instant feedback) and the server (never trust the client).

**API routes**
- Validate input, rate-limit with `checkRateLimit()` from `lib/rate-limit.ts`, return generic error messages, and never log passwords, OTPs or full request URLs that carry credentials.
- The rate limiter is in memory and per server instance: a best-effort first line of defence, not a guarantee on serverless hosting.
- Code that touches secrets or external credentials goes in `lib/server/` with `import "server-only"`.

**Security headers**
- `next.config.ts` sets a header-based CSP (no nonces, so pages stay static), HSTS and other security headers. Any new external script, image, font, iframe or fetch origin must be added to the CSP there, or the browser will block it.

**Navigation**
- Internal links use `next/link` (or `Button` with `href`), never a plain `<a href="/...">`.

**Native `<dialog>`**
- Open it with `showModal()` in an effect, and do not call `close()` in the effect cleanup: React's development double-mount would fire the `close` event and dismiss the dialog instantly. Close it by unmounting from the parent (see `app/(auth)/login/OtpDialog.tsx`).

## Login prototype (not production-safe)

The login is a deliberate prototype for client demos:

1. `LoginForm` posts the phone number and password to `/api/auth/login`.
2. The route normalizes the phone number to 10 digits and calls the vendor endpoint `POST {AEPS_API_BASE_URL}/GetV2LoginInfo_api?UserName=<phone>&Password=<password>` — a POST, but the parameters must be in the query string (a JSON body returns 404 "No action was found"). See `lib/server/aepsAuth.ts`; all vendor calls go through `aepsRequest()` in `lib/server/aepsClient.ts`.
3. With `Accept: application/json` the vendor returns a flat JSON object: `MESSAGE` (`"Success"` on valid credentials), `UserName`, `Otp`, `defaultOTP`, `Balance`, `walletBalance` (debit wallet), `CreditBalance` (credit wallet), `aepsBalance`, `bbpsBalance`, `cmsBalance`, `isAdmin`, and empty AEPS identity fields. All values are strings; codes can have leading zeros (e.g. `defaultOTP: "0022"`), so they are never converted to numbers. (The XML form wraps the same fields in `AEPSController.NPLoginResponse`; both are handled.)
4. On success the route stores `{ userName, password, isAdmin }` in the `namma_session` cookie (`lib/server/session.ts`): AES-256-GCM encrypted with `AUTH_SECRET`, httpOnly, 24-hour expiry (`SESSION_TTL_SECONDS` in `lib/auth/demoSession.ts`, shared with the stored profile) so a login lasts a full day, even across closing the browser. Later vendor calls read credentials from it. The password is never sent back to the browser or stored client-side.
5. The route returns the accepted codes and the balances to the browser. `OtpDialog` shows one box per digit and accepts the code if it equals either the SMS `Otp` or `defaultOTP`.
6. On a match the profile (balances only) is stored in `localStorage` with a 24h expiry (`lib/auth/demoSession.ts`) and the user lands on the first dashboard section. `DashboardShell` redirects to `/login` when there's no profile. Log out calls `/api/auth/logout` and clears both.

Known gaps — fix all of them before real users log in:
- The expected OTPs are sent to the browser, so anyone can read them in devtools; one of them is the account's fixed `defaultOTP`.
- The session cookie is set as soon as the vendor accepts the password, before the OTP step, and the OTP is checked only in the browser. Verify the OTP on the server and set the cookie only after it matches.
- The dashboard's "logged in" check reads `localStorage` (expires after 24h, like the cookie); `/login` redirects straight to the dashboard while it is valid; the real authority is the session cookie (report routes return 401 without it).
- The vendor API takes the password as a query parameter (even on the POST login endpoint), so it appears in this server's outbound URLs. Never log those URLs; ask the vendor to accept credentials in the request body.
- Login accepts either code the vendor returns: `Otp` (the per-request code sent to the customer by SMS) or `defaultOTP` (the fixed fallback) — `acceptedOtps` in the login response; the default one is listed first and sets the box count. The OTP boxes are never pre-filled.
- `SHOW_DEMO_OTP` in `app/(auth)/login/LoginForm.tsx` prints the expected OTP inside the modal when set to `true`.
- Vendor-side: `getapiLevelbalance` returns the real platform balances for a made-up username and password, and `PgTallyReport` and `GetBulkpeStatement` take no credentials at all — the role checks in our own routes are the only gate for the admin data. The same goes for `CreditCard/Statement` (Bulkpe CC Txns), which is also plain HTTP to a bare IP address.
- Vendor-side: `GetTxnsByDate` and `BpPayment/GetLinksByDate` need no password — anyone who knows a mobile number can fetch that account's AEPS transactions (including full Aadhaar numbers) and card payment collections (customer names, amounts) directly from the vendor. This app only ever passes the session's own number and masks Aadhaar, but the endpoint itself should require authentication.

## Dashboard

- `DashboardShell` (client) is the frame for every `/dashboard/*` page: top navbar with the logo (links to `/dashboard`), the wallet balances and the profile button, the navy sidebar (desktop) or slide-in drawer (mobile), and the content area. The shell is exactly one viewport tall (`h-dvh`, no page scrollbar): only `<main>` scrolls, and on tablet and up report tables fill the remaining height and scroll their rows internally (slim `scrollbar-light` / `scrollbar-dark` utilities in `globals.css`).
- The desktop sidebar is 14rem wide (`w-56`, kept narrow so the admin page's three panels get room) and collapses to icons only (`w-18`; labels become hover tooltips) via the toggle at its bottom; the choice is remembered in `localStorage` (`namma-sidebar-collapsed`). The mobile drawer always shows labels.
- Dashboard styling is flat and premium: navy gradient sidebar, no dot-grid textures or blurred glows.
- `WalletBalances` (navbar, `md` and up): two segments — **Debit balance** (`walletBalance`) and **Credit balance** (`CreditBalance`), in a light brand-styled chip. Values come from the login response, so they don't update until the next login.
- `ProfileMenu`: the profile button opens a panel with the phone number, total balance, the Debit wallet/Credit wallet/AEPS/BBPS/CMS balances and Log out. On phones this is the only place balances appear.
- Sidebar sections are defined once in `lib/data/dashboardNav.ts` (Transfer Reports, PG Reports, AEPS Reports, QR Reports, Bill Payments, Wallet Ledger, Credit Ledger, then the role-only Admin, Accountant, Filing, View History, Dispute History, Super Access); each has an icon in `components/dashboard/SectionIcon.tsx` and a page at `app/dashboard/<id>/page.tsx`.
- Role-only sections (`role` in `lib/data/dashboardNav.ts`) appear in a separate "Admin" sidebar group, each only for the account whose login flag matches (`hasPageRole()` in `lib/auth/adminAccess.ts`): **Admin** (`isAdmin`, shield icon, `/dashboard/admin`), **Accountant** (`isAccountant`, `/dashboard/accountant`) and **Super Access** (`isSuperAccess`, `/dashboard/super-access`). The flags come from the login response (matched by normalized field name in `aepsAuth.ts`; "accountant" / "superaccess" anywhere in a field name counts; the server logs which role flags the vendor sent), and are stored in the encrypted session cookie and the UI profile. Admin and Accountant show the same page content (`AdminOverview`: API balance, Today's Summary, PG Tally, Transfer Reports); Super Access shows `SuperAccessOverview`: a row of three boxes (`<ApiBalanceView bulOnly />`) — **Debit balance** first (the account's own `walletBalance` from the login, read from the stored profile like the navbar's "Debit balance"; the vendor has no live balance endpoint we can call, so it only changes at the next login — `POST {CLIENT_API_BASE_URL}/APIClient/CheckBalance` (JSON body, answers `{ status, MobileNumber, Balance, Message }`) exists and would give a live figure, but it answers "Invalid Authentication" to every credential form tried (login or mobile number in the body, Basic/Bearer/key headers), so its request format is unknown. The BUL total reloads every 30 s (`AUTO_REFRESH_MS`) and the Difference is recalculated from it each time), then the BUL total card (BUL 0724, 5512, 6633 and 6752), then **Difference** last (the blue card: debit balance − BUL total, with a ✓ at exactly 0; "—" while the debit balance is unknown; full-width boxes on phones) — and the PG Tally at full width (on desktop it fills the rest of the screen with its rows scrolling inside; on phones the BUL accounts stack as full-width rows and the tally is one card per collection). Each page wraps its content in `<AdminOnly role="…">`, which sends accounts without that flag back to the dashboard. That is UI only: every admin API route checks the session cookie on the server via `adminAccess()` — `api-balance` allows full (admin or accountant) and bul (super access; it returns only `bul_0724`, `bul_5512`, `bul_6633` and `bul_6752` — `SUPER_ACCESS_BUL_CODES` / `isSuperAccessBul` in `lib/admin/apiBalance.ts` — with the wallet, diff and every other account stripped server-side), `pg-tally` and `pg-tally/refresh` allow any logged-in account but **scope the rows by who is asking** (`tallyScope()` in `adminAccess.ts`): admins and accountants (the same) get every retailer's collections; super access gets only the collections whose retailer `userName` is the login's own number; a login with none of the three flags (a retailer) gets a 403 — retailers have no PG tally. The vendor's PgTallyReport can't filter (it ignores every parameter and returns the whole platform), so `fetchPgTally(from, to, owner)` filters on the server, before the settlement lookups; a super-access Refresh must name a collection that is in their own rows that day (the body carries `date`; otherwise 403), because the vendor's status check takes no credentials. `day-summary` requires full. Super access therefore sees only its own login's collections for now; showing the retailers *under* it needs the vendor's parent/client link, which the login response may carry — the login logs its field names (`AEPS login fields: …`, names only) to find it. 
- **Admin page** (`app/dashboard/admin/page.tsx` → `ApiBalanceView`): the API level balance. `GET /api/dashboard/admin/api-balance` (401 without a session, 403 if the session isn't admin) calls vendor `POST getapiLevelbalance?UserName=&Password=` (`lib/server/aepsAdmin.ts`), which returns `{ Status, StatusCode, Message, Data: { wallet, bul_0080, bul_8539, …, diff } }` with numeric values. Shown in one row, in this order: Difference (`diff`, with a ✓ when it equals wallet − the sum of all balances), API wallet (with `aepstotal` beside it in the same card — `isAepsTotal`), BUL total (sum of the `bul_*` accounts only — `isBulAccount`) with those accounts inside the same card, each with its share of the BUL total, then `aepsin` and `aepsout` together in one card (`isAepsInOut`), then the other balances (RUPE, unsettled, pending, …) together in one card, each with its share of all balances as text (no bars; unsettled/pending in navy — `isHeldBalance`) — on phones one balance per full-width row (label left, amount right); from `sm` up side by side, each at least 9rem wide so extra vendor keys (e.g. `invwithdrawal`) wrap to a new line instead of squeezing into overlapping text — all in one row (each card as wide as its content; they wrap only below ~1440px wide, and numbers step up a size from 1680px). Unsettled and pending balances (`isHeldBalance`: keys matching `unsettl`/`pend` — the vendor spells one `pendnig`) get navy-tinted cards; Difference is the blue (brand gradient) card, API wallet a plain one. It reloads itself every 30s (`AUTO_REFRESH_MS` in `ApiBalanceView`), quietly, skipping while the browser tab is hidden. What the `bul_` prefix stands for isn't documented, so accounts are labelled "BUL 0080" etc.
- **Bulkpe statement** (admin page, middle panel; `BulkpeStatementView`): every movement on the platform's Bulkpe payout account, newest first. `GET /api/dashboard/admin/bulkpe-statement?page=N` (401 without a session; 403 unless admin or accountant — super access doesn't get it; page 1–1000) calls vendor `GET {CLIENT_API_BASE_URL}/APIClient/GetBulkpeStatement?pageNo=N` (`fetchBulkpeStatement()` in `lib/server/aepsAdmin.ts`), which returns `{ status, page, count, data: [...] }`, 150 entries per page, page 1 = newest. **The vendor endpoint needs no credentials**, so our role check is the only gate. Only whitelisted fields reach the browser (`BulkpeEntry`, `lib/admin/bulkpeStatement.ts`): the virtual-account fields and the full account number are dropped (account shown as `••••7401`); the per-row `token` is the code of the BUL account the entry went through (`8539` = the "BUL 8539" balance card) and is sent as `bulAccount` ("BUL 8539"), shown as a chip beside the name, in the details and searchable; names get `_` → space; entries before `REPORTS_START_DATE` (or undated) are dropped, and `hasMore` is false once a page is short or hits that cut-off. The title row wraps on phones (balance under the title). **All three admin panels' rows share one fixed shape — two lines, `h-14` (56px) — with a `StatusText` pill beside the fee, a tag above the time (`RowTime`) and copy icons for the codes. PG Tally: Wallet Instant tag / name / NPPG + BPPG on one line (copy icons) and amount / fee + status + ✓ (or Refresh). Bulkpe: BUL account tag / name / `IFSC HDF…001 ⧉ UTR 630…203 ⧉` (first and last three characters, full code on copy; the reference for money in, the bank's red message for a failed one) and amount (tooltip: balance after) / one combined fee (charge + GST) + status. Below `@md` the time column, tag and pill shrink and the word "fee" is dropped; anything still too long is cut with "…" (full text on hover).** Click a row for every field (IDs, charges + GST, total debited, balance, both names, bank message, remark, created/updated). - **Admin page layout** (`AdminOverview` → `ApiBalanceView` with today's summary inline, then `AdminPanels`): the layout follows the **content area's width**, not the screen's (`AdminOverview` is a `@container`; `AdminPanels` uses `@3xl:`/`@5xl:` variants), so collapsing the sidebar gives the same result as a wider screen. 1. The page renders `<ReportView section="…" />`: title, From and To `DatePicker`s (no quick-range buttons; nothing before `REPORTS_START_DATE` can be picked — see "Report start date" below) (branded single-date calendars replacing the native date inputs, which browsers do not let us style) with an Apply button (default: today), and the table. There are no summary cards: everything sits in one toolbar above the table — tabs (if any), search, a compact Credit/Debit totals strip (reports with totals only; for all rows of the selected dates), the pager ("1–50 of 473" with ‹ › buttons, or "12 entries" on one page; 50 rows per page) and Export. On phones the toolbar wraps (search + Export, then totals + pager) and the pager repeats under the last card. A new page, tab or search scrolls the table back to its first row. Search matches every displayed column (including second lines such as the store under the vendor) plus the fields in `EXTRA_SEARCH_FIELDS` in `ReportView` — Transfer: `StoreName`, which isn't a column on the full page. A section can have tabs above the table (`reportViews` in `lib/reports/layouts.ts`) that filter the loaded rows on the client, each with a count — Transfer Reports has **All / Queue / Refundable / Refunded / Refresh** (Refunded = status "Refunded", see `isRefundedTransfer`): Queue = a dequeue/queue flag or a queued `TxnStatus` (never a refundable row, nor one with a final status such as Refunded/Success/Failed — the vendor leaves the queue flag set on refunded `…R1` rows), Refundable = a can-refund flag, Refresh = a can-refresh flag or (fallback) Success with no valid UTR yet, never a Refunded row, and for a super-access account that isn't an admin only transfers from `SUPER_ACCESS_REFRESH_FROM` (2026-11-02, `lib/reports/dates.ts`) on — that cut-off is applied in `ReportView` (`canCheck`, also deciding the Check icon), the rest of their report is unchanged — see `isQueuedTransfer`/`isRefundableTransfer`/`isRefreshableTransfer` in `lib/reports/table.ts`. The vendor has sent each of these flags under more than one field spelling (`CanRefund`/`canbeRefund`, `dequeue`/`AddToqueue`/`dequeueEnable`), so they're matched by the field's normalized name (case/separators stripped), not a fixed key — missing a spelling silently shows a tab as always-empty instead of erroring. Below the `md` breakpoint each entry is a card instead of a table row (`planCard()`): narration/customer (or the longest text field) as the title with the date underneath; amount plus Cr/Dr and status badges on the right; remaining fields as label-left/value-right rows; long IDs (reference, UTR) in a small footer line.
2. `ReportView` calls our API: `GET /api/dashboard/<section>?fromDate=yyyy-MM-dd&toDate=yyyy-MM-dd`. No credentials are sent. Every report re-loads itself every 30s (`AUTO_REFRESH_MS`), quietly — no loading state, page/tab/search/scroll kept — and skips while the browser tab is hidden, a row action is running or its popup is open; a failed reload keeps the data on screen.
3. `app/api/dashboard/<section>/route.ts` calls `handleReportRequest()` (`lib/server/reportRequest.ts`): rate limit, date validation (`validateRange`: From not before `REPORTS_START_DATE`, max 366 days; otherwise 400), credentials from the session cookie (401 if missing/expired), then `fetchReport()`.
4. `fetchReport()` (`lib/server/aepsReports.ts`) calls `GET {AEPS_API_BASE_URL}/<endpoint>` (or another `controller`, e.g. `…/api/BpPayment/<endpoint>`; or the client API with `api: "client"`; `method: "POST"` where the vendor needs it; asking for JSON when `prefer: "json"`) with that section's `params()`, applies its optional `transform()` to every row (fields it adds become columns), and finds the list of records in the XML/JSON response, whatever its wrapper names. The ledger endpoints wrap results in `AEPSController.txnsWallet { MESSAGE, data }`: `MESSAGE: "Success"` with `data` entries; **`MESSAGE: "Failed"` with `data` nil when the range simply has no transactions** (shown as an empty list, not an error); and `MESSAGE: "Cannot find table 0."` when the username/password is wrong (returned as 401 "session expired", so the UI offers "Log in again"; a vendor HTTP 401, as the client API sends, is treated the same). Other messages like "no records found" also become an empty list; any other non-success message is returned as a 422 and logged (message and response shape only).
5. Columns come from the vendor's field names; `lib/reports/table.ts` infers formatting (₹ amounts with credit/debit colours, dates, Cr/Dr and status badges) and hides columns that are empty in every row. The vendor's dates are .NET en-US strings (`10/3/2026 5:46:26 PM` = month/day/year); `parseDate` handles them as well as ISO and `/Date(…)/`, and shows them as `03 Oct 2026, 5:46 pm` (no time when it's exactly midnight).
6. A section can instead have a fixed column order in `lib/reports/layouts.ts`. **Wallet Ledger** uses: Date & Time, Type, Narration, Amount, Cr/Dr, Closing Balance. **AEPS Reports** uses: Date & Time, Type, Aadhaar, Amount, Credited (counted as Total credit), User CB, Remarks, UTR. **PG Reports** uses: Date & Time, Customer, Card, Amount (charged to card), Charges, Credited (to bank; Total credit), Settlement, Status, Reference. **Transfer Reports** uses: Date & Time, Txn ID, Sender, Beneficiary, Account / IFSC (IFSC on a second line via the slot's `sub`; two separate CSV columns), Amount, Charges (the vendor's `Fee` field — the transfer charge; `hideBelow: "lg"`; neutral tone, so it's never counted in the totals), UTR, Status, Remarks. A slot's `format: "code"` sets IDs and numbers in monospace and never breaks them across lines; `format: "words"` wraps names and remarks only between words. When a report has a Status column, summary totals count only SUCCESS rows (failed/pending/refunded moved no money). Tables must not scroll sideways: in the table, dates stack (date over time), text wraps (max two lines), long IDs use small monospace, and a slot can set `hideBelow: "lg" | "xl" | "2xl"` to drop a less important column on narrower screens (PG hides Charges below lg and Settlement/Reference below xl; AEPS hides Aadhaar below lg and User CB/UTR below xl; Transfer hides Txn ID and Charges below lg, Account / IFSC and UTR below xl, and Sender/Remarks below 2xl). Hidden columns stay in the mobile cards, search and CSV export. Each slot lists the vendor field names it accepts; Cr/Dr is also recognised by its values; when the vendor sends a date-only field plus a second date-time (or time) field, the Date & Time cell shows the complete value once (`dateCellText` in `lib/reports/table.ts`); separate credit/debit amount fields become one Amount; Amount is coloured per row by Cr/Dr. If fewer than 3 slots match, every field is shown instead. In development the server logs each report's field names (`AEPS <endpoint> fields: …`, names only) to help adjust the patterns.
7. **Export CSV** (`toCsv` in `lib/reports/table.ts`) writes the layout's columns for the rows of the current tab and search (every page, not just the one on screen; the file name includes the tab, e.g. `transfer_refundable_…csv`) — **except for a super-access account** (`isSuperAccess`), whose export ignores the selected tab and contains every row of the dates (the search still applies; the file name has no tab) in a form Excel opens correctly: a UTF-8 byte order mark (added in `ReportView`; without it `•` and `₹` are garbled), CRLF line endings, dates as `yyyy-MM-dd HH:mm` (real, sortable Excel dates), amounts exactly as the vendor sent them minus thousands separators (plain numbers Excel can sum, never rounded; the dashboard's totals skip non-SUCCESS rows and split Cr/Dr, so reproduce them in Excel with SUMIF), and digit-only IDs of 12+ digits or with a leading zero (PG reference, UTR) as `="…"` so Excel keeps them as text instead of `6.10261E+20` with the digits after the 15th lost. Text starting with `=`, `+`, `-` or `@` gets a leading `'` so vendor data (customer names, remarks) can't run as a formula (CSV injection).

**Bill payment disputes.** **Raising** (everyone): the Bill Payments table has a **Dispute** column right after Status (phone cards: beside the status badge) — a **Raise dispute** button on every row, or, once the transaction has a dispute, a status chip ("Dispute open" / "Dispute resolved", the admin's remarks in the tooltip), and, only on a payment whose dispute is **open** (not on resolved ones or ones with no dispute), a round **refresh icon** beside the chip (`DisputeCell` + `PaymentStatusDialog`) that checks the payment's live status: `POST /api/dashboard/bill-payments/disputes/payment-status { uniqueId }` (any logged-in account, rate-limited — the vendor does no ownership check) → `fetchPaymentStatus()` in `lib/server/aepsDisputes.ts` → vendor `GET …/bill/getPaymentStatusByRef?refNo=<UniqueId>` (no credentials; answers `{ status: "true", data: [{ UniqueId, npciRef, amount, dateTime, bankName, cardNumber, mobileNumber, status }] }`); the popup shows amount, status, bank, card last 4, mobile, time, NPCI ref and the bill reference — never the UniqueId, which the route drops. The Disputes tab itself has no such icon. The button opens `RaiseDisputeDialog` (`components/dashboard/RaiseDispute.tsx`: what went wrong, 5–300 characters) → `POST /api/dashboard/bill-payments/disputes/raise { uniqueId, billPaidRefNo, reason, userName? }` (401 without a session, rate-limited, 20 per 10 minutes) → `raiseDispute()` in `lib/server/aepsDisputes.ts` → vendor `POST …/v5bc/api/bill/raiseDispute` with a JSON body `{ uniqueId, userName, reason, billPaidRefNo }`; `uniqueId` is the row's `UniqueId` (the "REFL…" id; not a shown column) and `billPaidRefNo` its bill reference. `userName` is the session's login number — only admins and accountants (whose Bill Payments rows are every retailer's) may send another retailer's number, taken from the row's `username`. The chips come from `useBillDisputes` → `GET …/disputes?status=ALL`, which returns **the caller's own disputes** (`userName` from the session) or, for admins and accountants, every retailer's; it loads when the page opens and after a dispute is raised, and joins on `UniqueId`. The vendor endpoint takes no credentials and the route can't confirm a bill payment belongs to the caller. **Disputes tab** (admins and accountants only). The Bill Payments page (`BillPaymentsView`) gets a **Disputes** tab next to the report for accounts with `isAdmin` or `isAccountant` (UI only; both tabs stay mounted); everyone else gets just the report. `BillDisputesPanel`: a status `FilterSelect` (Open / Resolved / All), search over every field, Refresh, and one row per dispute (created time, retailer number and `#id`, reason, the bill reference (`BillPaidRefNo`) with a copy icon — the transaction id (`UniqueId`) is not shown, not even in "All fields" — admin remarks and the resolved date, a status pill, **Resolve** on OPEN ones and an "All fields" expander that lists every field the vendor sent). It loads when opened, on a filter change and on Refresh — no auto-reload. Routes (the tab's `update` route is 401 without a session and 403 unless `adminAccess() === "full"`; both rate-limited, since the vendor endpoints need no credentials): `GET /api/dashboard/bill-payments/disputes?status=OPEN|RESOLVED|ALL` → `fetchDisputes()` in `lib/server/aepsDisputes.ts` → vendor `GET https://nammapayments.in/v5bc/api/bill/getDisputes?status=` (reached through `aepsRequest(…, { controller: "bill" })`; `userName` is left out so every retailer's disputes come back; answers `{ status: "true", data: [...] }`; `ALL` sends no status), and `POST /api/dashboard/bill-payments/disputes/update { id, adminRemarks }` → `updateDispute()` → vendor `POST …/api/bill/updateDispute` with a JSON body `{ id, status: "RESOLVED", adminRemarks }` (the one vendor call that takes a body — `aepsRequest`'s `body` option; only RESOLVED can be set from here; remarks required, at most 500 characters). The Resolve dialog asks for the remarks, then reloads the list. **How the vendor's endpoints behave (checked against the live API once, with made-up ids):** `getDisputes` rows are `{ Id, UniqueId, UserName, Reason, Status ("OPEN" / "RESOLVED"), RaisedAt, ResolvedAt, AdminRemarks, BillPaidRefNo }` (nulls for what isn't set yet; an unknown `status` filter just lists nothing; with no parameters it lists everything); `raiseDispute` and `updateDispute` need a JSON body (a query string gets HTTP 411) and answer `{ status: "true", data: [{ Success: true, Message: "Dispute raised", Id }] }` / `data: [{ Success: true, Message: "Updated" }]`, while a failure is `{ status: "false", message }` carrying the database's raw error text (table and column names), so `readWriteResult()` in `lib/server/aepsDisputes.ts` logs it and shows a generic message instead. **The vendor validates nothing:** `raiseDispute` accepted a transaction id that doesn't exist (it needs all four fields — an empty body fails on `UniqueId` — but not that the transaction exists or belongs to `userName`), and `updateDispute` answered "Updated" for an id that doesn't exist. The API's database is named like a test database (`Sample_test_V5_BC`). `disputeView()` in `lib/admin/disputes.ts` finds the fields by normalized name and the "All fields" view shows the rest. Vendor-side gap: these three endpoints take no credentials either.

**Transfer row actions.** None of these reload the whole report:
- **Check** (`CheckStatusButton`, `TransferStatusDialog`): the Transfer Reports table has a **Check** column right after Status with a round refresh icon, only on the rows that are in the **Refresh** tab (`isRefreshableTransfer`; the column itself is hidden while no row qualifies) (in the admin panel's list the icon sits beside the status pill; phone cards put it beside the badges). Clicking it opens a popup straight away ("Checking the status…") and calls `POST /api/dashboard/transfer/status { uniqueId }` (session-gated, rate-limited; `uniqueId` is the row's `UniqueTxnId`, validated `[A-Za-z0-9_-]{1,40}`) → `checkTransferStatus()` in `lib/server/aepsActions.ts` → vendor `GET {AEPS_API_BASE_URL}/checkBulkpeStatus?uniqueId=` (no credentials; a POST fails with 411), which answers `{ status: "true", uniqueId, displayStatus, displayRemarks, utr, canRefund, isAddQueue }` plus, only for transfers the payout partner already knows, `channel`, `amount` and `txnTime` (for one it has no record of yet — `found: false`, seen on Pending transfers — those three are missing and `hours` (age) / `waitHours` (how long the vendor waits before a refund is possible, e.g. 26) come instead; `channelTxnId`, `apiRef`, `bulkpeStatus`, `raws` are ignored), or `{ status: "false", message: "transaction not found" }` (HTTP 200 both ways). The popup shows the beneficiary (from the report row, since the vendor's answer has no name), the amount (large; the vendor's, else the report row's `Amount`), status, remarks, UTR (copy icon), time (`txnTime` is India wall-clock without a timezone, shown as written; else the report row's time), can be refunded (`canRefund`), can be queued again (`isAddQueue`) and the Txn ID; an unknown id shows the vendor's message. When the live status says **Can be refunded: Yes** the popup gets a **Refund** button, and **Can be queued again: Yes** an **Enqueue** button (hidden when the row has no vendor row id — `transferRowId()`, which is what those actions take, not the Txn ID): clicking one closes the popup and runs the normal row action (`requestTransferAction`: Refund asks for confirmation first, then the result popup). The check itself never changes the table. Vendor-side gap: like the other endpoints above, `checkBulkpeStatus` needs no authentication, so anyone with a transaction id can read its amount and UTR; our session check is the only gate and there is no ownership check (same as Dequeue/Enqueue/Refund).
- **Refresh** (`RefreshUtrButton`; currently switched off via `ROW_REFRESH_ENABLED = false` in `ReportView`): shown in place of the UTR value when `isRefreshableTransfer()` is true. There's no single-transaction vendor endpoint, so `refreshRow()` in `ReportView` re-runs the date-range report and patches just that one row into `state.table.rows` (same position, not a full reload), then shows `RefreshResultDialog` with the row's latest status/UTR/beneficiary.
- **Dequeue / Enqueue / Refund** (`TransferActionButton`, one `TransferAction` each): shown next to the Status cell. Enqueue and Refund show together when `isRefundableTransfer()` is true; Dequeue shows only when `isQueuedTransfer()` is true **and** the row isn't refundable — refundable takes over Dequeue when both would otherwise apply, so a row shows either just Dequeue or both Enqueue and Refund, never all three. Refund first asks for confirmation (`ConfirmRefundDialog`: amount, beneficiary, Cancel/Refund) and only calls the vendor after the second click; Dequeue and Enqueue run straight away. Any of them — only when the row has an id (`transferRowId()` — the vendor's internal id for the row, field name not fixed, same normalized-name matching as the flags above; seen as `3368814`-style short numbers). Each calls `POST /api/dashboard/transfer/<dequeue|enqueue|refund> { id }` (one-line route per action, all forwarding to `handleTransferAction()` in `lib/server/transferActionRequest.ts`: session-gated and rate-limited) → `callTransferAction()` in `lib/server/aepsActions.ts` → vendor `POST {CLIENT_API_BASE_URL}/Txn/<UpdateDequeue|UpdateEnqueue|ProcessRefund>?id=` (GET returns HTTP 405; confirmed via production logs), confirmed response `{ status: boolean, message: string, id: string }`. No password and no updated row come back, so clicking one opens `TransferActionResultDialog` immediately in a "Requesting…" state, then shows the vendor's own message/error and the id that was sent; on success it patches just that row locally (and after a Dequeue the report quietly reloads 10s later, so the vendor's Refundable state shows up; the result popup stays open and can't be dismissed during that 10s countdown) (`applyTransferActionPatch`: Dequeue → status "Dequeued" with queue flags cleared, Enqueue → "In Queue", Refund → "Refunded" with refund flags cleared), since the vendor returns no new row data; re-apply the date range to see the vendor's real state.

**Report start date.** No report shows anything dated before `REPORTS_START_DATE` (`2026-10-07`, in `lib/reports/dates.ts`), and the server enforces it twice: `validateRange` rejects a From date before it (HTTP 400, so a hand-made request can't ask for older data), and `fetchReport` drops every row the vendor returns whose date (the first `date`/`time` field that parses, compared as the vendor's own wall-clock date) is earlier — or that has no readable date at all. PG Reports starts earlier, on `2026-10-04` (`SECTION_START_DATES` / `reportStartDate(section)` in `lib/reports/dates.ts`; `validateRange`, `fetchReport` and the pickers all use the section's date). The date pickers only mirror the limit. Changing it needs a code change and a deploy. **Admins have no start date** (`isAdmin` only — accountants, super access and retailers keep it): the server reads the flag from the encrypted session cookie and passes `noStartDate` to `validateRange` (report routes, `pg-tally`, `api-balance/history`) and `fetchBulkpeStatement`, and `fetchReport` skips its row filter, so admins also get rows with no readable date. `ReportView` and `DifferenceHistoryView` read `isAdmin` from the stored profile only to free the From picker; changing that in the browser gets a 400 from the server. The 366-day maximum range still applies to everyone.

To connect another section: add its endpoint, `params()` and any `transform()` to `REPORT_ENDPOINTS` in `lib/server/aepsReports.ts`, create `app/api/dashboard/<section>/route.ts` (one line: `return handleReportRequest(request, "<section>")`), and render `<ReportView section="<section>" />` on its page.

`FromDate`/`ToDate` are sent as `yyyy-MM-dd` (`VENDOR_DATE_FORMAT` in `lib/server/aepsReports.ts`), confirmed against the live ledger endpoints.
