# NammaAPI — project guide

`next dev` only rewrites the block above, between its markers. Everything below is maintained by hand; keep it accurate when the code changes.

## What this project is

Marketing website for **NammaAPI**, a business payments API platform for Indian businesses (payouts, payment collection, salary & bulk payments, payment automation), plus a **prototype phone + OTP login** backed by an external AEPS API.

- Next.js 16 (App Router, Turbopack), React 19, TypeScript (strict), Tailwind CSS v4.
- Every page is statically prerendered. The only dynamic routes are the API routes under `app/api/`.
- No database. The contact form emails via Resend; login calls the external AEPS API.

## Conventions

**Rendering**
- Server Components by default. Add `"use client"` only for interactivity. Current client components: `Header`, `ChatWidget`, `CodeTabs`, `FormInput`, the contact/signup/login forms, `OtpDialog`, `DashboardShell`, `DashboardSidebar`, `ProfileMenu`, and the error boundaries.
- Page chrome comes from layouts, not the root layout: public pages live in `app/(site)/` (website navbar and footer), the login page in `app/(auth)/` (no chrome), logged-in pages in `app/dashboard/` (dashboard shell). A new public page goes in `app/(site)/`. `app/not-found.tsx` renders outside all of them, so it adds `Header`/`Footer` itself.
- Keep pages static. Request-time APIs (`cookies()`, `headers()`, `searchParams`) in a page or layout make it dynamic.
- Error boundaries receive `retry` (Next 16), not `reset`.

**Content and data**
- Page copy lives in `lib/data/*.ts` and is rendered by components. Add products, industries or nav links there, not inline in JSX.
- Form option lists (business types, volumes, services) live in `lib/data/leadOptions.ts` and are shared by forms and server validation.

**Metadata and SEO**
- Every page exports `metadata = buildMetadata({ title, description, path })`. It appends `| NammaAPI`, sets the canonical URL and the shared Open Graph/Twitter image. Use `—`, not `|`, inside titles.
- Pass `noIndex: true` for pages that shouldn't be indexed (login, signup, dashboard), and keep them out of `app/sitemap.ts`.

**Styling**
- Use the theme tokens in `app/globals.css` (`brand-primary`, `brand-navy`, `text-secondary`, ...). `status-*` colors are only for transaction/status UI.
- Join classes with `cn()` from `lib/cn.ts`; it runs tailwind-merge, so a `className` passed to a component overrides its defaults.
- Animations are defined in `@theme` in `app/globals.css`; a global `prefers-reduced-motion` rule disables them.

**Forms and validation**
- Use `FormInput` / `FormSelect` / `FormTextarea`: they render the label, the required marker, and error/hint text wired up with `aria-describedby`.
- Validate with the shared functions in `lib/validation/` on both the client (instant feedback) and the server (never trust the client).

**API routes**
- Validate input, rate-limit with `checkRateLimit()` from `lib/rate-limit.ts`, return generic error messages, and never log passwords, OTPs or full request URLs that carry credentials.
- The rate limiter is in memory and per server instance: a best-effort first line of defence, not a guarantee on serverless hosting.
- Code that touches secrets or external credentials goes in `lib/server/` with `import "server-only"`.

**Security headers**
- `next.config.ts` sets a header-based CSP (no nonces, so pages stay static), HSTS and other security headers. Any new external script, image, font, iframe or fetch origin must be added to the CSP there, or the browser will block it.

**Navigation**
- Internal links use `next/link` (or `Button` with `href`), never a plain `<a href="/...">`.

**Native `<dialog>`**
- Open it with `showModal()` in an effect, and do not call `close()` in the effect cleanup: React's development double-mount would fire the `close` event and dismiss the dialog instantly. Close it by unmounting from the parent (see `app/(auth)/login/OtpDialog.tsx`).

## Login prototype (not production-safe)

The login is a deliberate prototype for client demos:

1. `LoginForm` posts the phone number and password to `/api/auth/login`.
2. The route normalizes the phone number to 10 digits and calls the vendor endpoint `POST {AEPS_API_BASE_URL}/GetV2LoginInfo_api?UserName=<phone>&Password=<password>` — a POST, but the parameters must be in the query string (a JSON body returns 404 "No action was found"). See `lib/server/aepsAuth.ts`; all vendor calls go through `aepsRequest()` in `lib/server/aepsClient.ts`.
3. With `Accept: application/json` the vendor returns a flat JSON object: `MESSAGE` (`"Success"` on valid credentials), `UserName`, `Otp`, `defaultOTP`, `Balance`, `walletBalance` (debit wallet), `CreditBalance` (credit wallet), `aepsBalance`, `bbpsBalance`, `cmsBalance`, `isAdmin`, and empty AEPS identity fields. All values are strings; codes can have leading zeros (e.g. `defaultOTP: "0022"`), so they are never converted to numbers. (The XML form wraps the same fields in `AEPSController.NPLoginResponse`; both are handled.)
4. On success the route stores `{ userName, password, isAdmin }` in the `namma_session` cookie (`lib/server/session.ts`): AES-256-GCM encrypted with `AUTH_SECRET`, httpOnly, 24-hour expiry (`SESSION_TTL_SECONDS` in `lib/auth/demoSession.ts`, shared with the stored profile) so a login lasts a full day, even across closing the browser. Later vendor calls read credentials from it. The password is never sent back to the browser or stored client-side.
5. The route returns `defaultOTP` and the balances to the browser. `OtpDialog` shows one box per digit and accepts the code only if it equals `defaultOTP`.
6. On a match the profile (balances only) is stored in `localStorage` with a 24h expiry (`lib/auth/demoSession.ts`) and the user lands on the first dashboard section. `DashboardShell` redirects to `/login` when there's no profile. Log out calls `/api/auth/logout` and clears both.

Known gaps — fix all of them before real users log in:
- The expected OTP is sent to the browser, so anyone can read it in devtools; and it is the account's fixed `defaultOTP`, not the per-request `Otp`.
- The session cookie is set as soon as the vendor accepts the password, before the OTP step, and the OTP is checked only in the browser. Verify the OTP on the server and set the cookie only after it matches.
- The dashboard's "logged in" check reads `localStorage` (expires after 24h, like the cookie); `/login` redirects straight to the dashboard while it is valid; the real authority is the session cookie (report routes return 401 without it).
- The vendor API takes the password as a query parameter (even on the POST login endpoint), so it appears in this server's outbound URLs. Never log those URLs; ask the vendor to accept credentials in the request body.
- Login accepts either code the vendor returns: `Otp` (the per-request code sent to the customer by SMS) or `defaultOTP` (the fixed fallback) — `acceptedOtps` in the login response; the default one is what gets pre-filled when `PREFILL_DEFAULT_OTP` is on. `PREFILL_DEFAULT_OTP` (off) in `app/(auth)/login/LoginForm.tsx` pre-fills the OTP boxes with the expected code, so login is Verify-only — turn it off before real users log in.
- `SHOW_DEMO_OTP` in `app/(auth)/login/LoginForm.tsx` prints the expected OTP inside the modal when set to `true`.
- Vendor-side: `GetTxnsByDate` and `BpPayment/GetLinksByDate` need no password — anyone who knows a mobile number can fetch that account's AEPS transactions (including full Aadhaar numbers) and card payment collections (customer names, amounts) directly from the vendor. This app only ever passes the session's own number and masks Aadhaar, but the endpoint itself should require authentication.

## Dashboard

- `DashboardShell` (client) is the frame for every `/dashboard/*` page: top navbar with the logo (links to `/dashboard`), the wallet balances and the profile button, the navy sidebar (desktop) or slide-in drawer (mobile), and the content area. The shell is exactly one viewport tall (`h-dvh`, no page scrollbar): only `<main>` scrolls, and on tablet and up report tables fill the remaining height and scroll their rows internally (slim `scrollbar-light` / `scrollbar-dark` utilities in `globals.css`).
- The desktop sidebar collapses to icons only (labels become hover tooltips) via the toggle at its bottom; the choice is remembered in `localStorage` (`namma-sidebar-collapsed`). The mobile drawer always shows labels.
- Dashboard styling is flat and premium: navy gradient sidebar, no dot-grid textures or blurred glows.
- `WalletBalances` (navbar, `md` and up): two segments — **Debit balance** (`walletBalance`) and **Credit balance** (`CreditBalance`), in a light brand-styled chip. Values come from the login response, so they don't update until the next login.
- `ProfileMenu`: the profile button opens a panel with the phone number, total balance, the Debit wallet/Credit wallet/AEPS/BBPS/CMS balances and Log out. On phones this is the only place balances appear.
- Sidebar sections are defined once in `lib/data/dashboardNav.ts` (Transfer Reports, PG Reports, AEPS Reports, QR Reports, Bill Payments, Wallet Ledger, Credit Ledger, Admin); each has an icon in `components/dashboard/SectionIcon.tsx` and a page at `app/dashboard/<id>/page.tsx`.
- Sections marked `adminOnly: true` (currently **Admin**, shield icon) appear in a separate "Admin" sidebar group only when the login response has `isAdmin: true`. Their pages wrap content in `<AdminOnly>`, which sends non-admins back to the dashboard. That is UI only: `isAdmin` is also stored in the encrypted session cookie, and any admin API route must check `(await getSessionCredentials())?.isAdmin` on the server.
- **Admin page** (`app/dashboard/admin/page.tsx` → `ApiBalanceView`): the API level balance. `GET /api/dashboard/admin/api-balance` (401 without a session, 403 if the session isn't admin) calls vendor `POST getapiLevelbalance?UserName=&Password=` (`lib/server/aepsAdmin.ts`), which returns `{ Status, StatusCode, Message, Data: { wallet, bul_0080, bul_8539, …, diff } }` with numeric values. Shown as: API wallet, BUL total (sum of every `bul_*`/other key), Difference (`diff`, with a "Matches" badge when it equals wallet − BUL total), and one card per account with its share of the BUL total. It reloads itself every 30s (`AUTO_REFRESH_MS` in `ApiBalanceView`), quietly, skipping while the browser tab is hidden. What the `bul_` prefix stands for isn't documented, so accounts are labelled "BUL 0080" etc.
- **Admin page layout**: API Level Balance full width; below it PG Tally and a compact Transfer Reports panel side by side (`xl:grid-cols-2`, stacked below xl). The panel is `<ReportView section="transfer" compact columnLayout="admin-transfer" />` in a fixed-height box — `compact` gives a small title with the dates stacked under it and fills the parent's height; `columnLayout` picks a named layout from `columnLayouts` in `lib/reports/layouts.ts` (by name, because slots hold RegExps that can't cross from a Server Component). `adminTransferColumns`: Date & Time, Beneficiary / Amount (amount under the name, via a slot `sub` with `kind: "amount"` → `ColumnInfo.subKind`), Vendor / Shop (`Channel` with `StoreName` under it), UTR, Status. The full Transfer Reports page is unchanged. `PgTallyView` sizes itself with container queries (`@container`, `@lg:`/`@5xl:`/`@6xl:`), not screen breakpoints, so it lays out by its own width: at half width the Reference column hides, the amount shows just the fee, and the credit date drops the year.
- **PG tally** (admin page, below the balance; `PgTallyView`): card collections vs the wallet credits they should produce. `GET /api/dashboard/admin/pg-tally?fromDate=&toDate=` (401 without a session, 403 if not admin; same date rules as PG Reports) calls vendor `POST PgTallyReport?from=&to=` (GET returns 405; no credentials needed, so none are sent) via `fetchPgTally()` in `lib/server/aepsAdmin.ts`. One row per collection: `DebitFromCard` (charged to the card), `Charges`, `Amount` (credited = card − charges), `PaymentStatus` SUCCESS/PENDING/FAILED and `WalletCreditCount`. The vendor also sends `WalletCredited` (boolean): true counts as credited even when `WalletCreditCount` is still 0 (seen on collections settled by a direct bank payout). `tallyCheck()` in `lib/admin/pgTally.ts` flags what needs looking at: SUCCESS credited 0 times ("Not credited") or 2+ times ("Credited twice"), and a non-success row that was credited. Laid out like Transfer Reports but compact: one line with the title and From/To pickers (no icon or subtitle), then one card with a toolbar (tabs All / To check / Success / Pending / Failed with counts, a retailer filter — the grouping — search, and a Collected/Credited totals strip for the selected retailer) and a table: Date & Time, Retailer (name, mobile underneath), Reference / Collection ID (both in one cell, lg and up), Amount (credited, with "card − fee" underneath), Status and Wallet badges (the wallet credit date and time — `WalletCreditTime` — under the badge). Rows to check are tinted and sorted to the top; phones get one card per collection. Rows the vendor marks `CanRefresh: true` get a **Refresh** button in the Wallet cell: `POST /api/dashboard/admin/pg-tally/refresh { referenceNumber, collectionId }` (admin-only, rate-limited) → `checkBpayStatus()` → vendor `POST bpayStatusCheck_admin?referenceNumber=<NPPG… reference>&pgOrderId=<collection ID>` (vendor signature `[HttpPost] bpayStatusCheck_admin(string referenceNumber, string pgOrderId)`). Confirmed response: `{ status: "true", statusCode, total, data: [{ collectionId, charge, gst, additionalCharge, status, message, utr, payouts: [{ accountNumber, ifsc, beneficiaryName, holderName, status, message, paymentMode, utr }] }] }` (all strings). The popup shows the status and message, collection ID, UTR, fees (charge + GST + additional) and each payout (beneficiary, account masked to its last 4 digits server-side, IFSC, mode, status, UTR, message); `status` not "true" or no `data` is shown as an error. The tally reloads afterwards. Re-loads quietly every 30s like the reports.
- Sections without real content render `SectionPlaceholder` (header + empty state). To add a section: add it to `dashboardSections`, give it an icon, and create its page.

## Dashboard reports

Sections backed by a vendor date-range endpoint (configured in `REPORT_ENDPOINTS`, `lib/server/aepsReports.ts`):

| Section | Vendor call | Notes |
| --- | --- | --- |
| **Transfer Reports** (`transfer`) | `POST {CLIENT_API_BASE_URL}/transfer/report?UserName=&Password=&FromDate=&ToDate=` (`api: "client"`; parameters in the query string) | JSON array of `{ time, Amount, BeneficiaryAccntNumber, BeneficiaryName, BeneficiaryIFSCcode, UTR, SenderMobileNumber, StoreName, Channel, TxnStatus, dequeue, CanRefund, Remarks, UniqueTxnId }`; `[]` for an empty range; HTTP 401 "Invalid username or password" for wrong credentials (→ "session expired"). A refunded transfer still has `TxnStatus: "success"` but `Remarks: "Refunded/Oct  6 2026  3:47PM"`, `UTR: "-"` and an ID ending in `R1`: the transform sets its status to "Refunded" (so totals skip it) and the remark to "Refunded on 6 Oct 2026, 3:47 pm". It also capitalises statuses ("In Queue") and all-caps remarks ("COMPLETED" → "Completed"), blanks UTRs that are `-` or just repeat the transaction ID (queued transfers), and replaces `_` in beneficiary names. `Channel` (the vendor's payout partner) and `StoreName` (the user's own) aren't shown. |
| **Wallet Ledger** | `GET GetWalletTransactions?UserName=&Password=&FromDate=&ToDate=` | XML `AEPSController.txnsWallet` |
| **Credit Ledger** | `GET GetWalletTransactions_swallet?…` (same params) | same shape |
| **AEPS Reports** | `GET GetTxnsByDate?fromDate=&toDate=&mobileNumber=` | JSON array of `{ timestamp, transactiontype, adhaarnumber, mobilenumber, amount, userCreditAmount, userCB, remarks, UTR }`. No password; `mobileNumber` is always the session's username, never taken from the browser. Server-side transform masks Aadhaar to `XXXX XXXX 1234` (never sent in full) and maps type codes (CW, BE, MS, AP, CD) to names. "userCB" isn't documented, so it's labelled "User CB". |
| **PG Reports** | `GET …/api/BpPayment/GetLinksByDate?fromDate=&toDate=&mobileNumber=` (controller `BpPayment`, not `aeps`) | JSON array of card payment collections (`createdDateTime`, `custName`, `cardType`, `CardNumber` = last 4 only, `DebitFromCard`, `Charges`, `amountCreditToBank`, `settlementType`, `status` SUCCESS/FAILED/PENDING, `referenceNumber`, plus IDs and mostly-null fields). No password; number from the session. Transform adds `card` ("•••• 5968", last 4 digits only) and makes `settlementType` readable ("Wallet 24 Hours"). |

1. The page renders `<ReportView section="…" />`: title, From and To `DatePicker`s (no quick-range buttons; nothing before `REPORTS_START_DATE` can be picked — see "Report start date" below) (branded single-date calendars replacing the native date inputs, which browsers do not let us style) with an Apply button (default: today), and the table. There are no summary cards: everything sits in one toolbar above the table — tabs (if any), search, a compact Credit/Debit totals strip (reports with totals only; for all rows of the selected dates), the pager ("1–50 of 473" with ‹ › buttons, or "12 entries" on one page; 50 rows per page) and Export. On phones the toolbar wraps (search + Export, then totals + pager) and the pager repeats under the last card. A new page, tab or search scrolls the table back to its first row. A section can have tabs above the table (`reportViews` in `lib/reports/layouts.ts`) that filter the loaded rows on the client, each with a count — Transfer Reports has **All / Queue / Refundable / Refunded / Refresh** (Refunded = status "Refunded", see `isRefundedTransfer`): Queue = a dequeue/queue flag or a queued `TxnStatus` (never a refundable row, nor one with a final status such as Refunded/Success/Failed — the vendor leaves the queue flag set on refunded `…R1` rows), Refundable = a can-refund flag, Refresh = a can-refresh flag or (fallback) Success with no valid UTR yet — see `isQueuedTransfer`/`isRefundableTransfer`/`isRefreshableTransfer` in `lib/reports/table.ts`. The vendor has sent each of these flags under more than one field spelling (`CanRefund`/`canbeRefund`, `dequeue`/`AddToqueue`/`dequeueEnable`), so they're matched by the field's normalized name (case/separators stripped), not a fixed key — missing a spelling silently shows a tab as always-empty instead of erroring. Below the `md` breakpoint each entry is a card instead of a table row (`planCard()`): narration/customer (or the longest text field) as the title with the date underneath; amount plus Cr/Dr and status badges on the right; remaining fields as label-left/value-right rows; long IDs (reference, UTR) in a small footer line.
2. `ReportView` calls our API: `GET /api/dashboard/<section>?fromDate=yyyy-MM-dd&toDate=yyyy-MM-dd`. No credentials are sent. Every report re-loads itself every 30s (`AUTO_REFRESH_MS`), quietly — no loading state, page/tab/search/scroll kept — and skips while the browser tab is hidden, a row action is running or its popup is open; a failed reload keeps the data on screen.
3. `app/api/dashboard/<section>/route.ts` calls `handleReportRequest()` (`lib/server/reportRequest.ts`): rate limit, date validation (`validateRange`: From not before `REPORTS_START_DATE`, max 366 days; otherwise 400), credentials from the session cookie (401 if missing/expired), then `fetchReport()`.
4. `fetchReport()` (`lib/server/aepsReports.ts`) calls `GET {AEPS_API_BASE_URL}/<endpoint>` (or another `controller`, e.g. `…/api/BpPayment/<endpoint>`; or the client API with `api: "client"`; `method: "POST"` where the vendor needs it; asking for JSON when `prefer: "json"`) with that section's `params()`, applies its optional `transform()` to every row (fields it adds become columns), and finds the list of records in the XML/JSON response, whatever its wrapper names. The ledger endpoints wrap results in `AEPSController.txnsWallet { MESSAGE, data }`: `MESSAGE: "Success"` with `data` entries; **`MESSAGE: "Failed"` with `data` nil when the range simply has no transactions** (shown as an empty list, not an error); and `MESSAGE: "Cannot find table 0."` when the username/password is wrong (returned as 401 "session expired", so the UI offers "Log in again"; a vendor HTTP 401, as the client API sends, is treated the same). Other messages like "no records found" also become an empty list; any other non-success message is returned as a 422 and logged (message and response shape only).
5. Columns come from the vendor's field names; `lib/reports/table.ts` infers formatting (₹ amounts with credit/debit colours, dates, Cr/Dr and status badges) and hides columns that are empty in every row. The vendor's dates are .NET en-US strings (`10/3/2026 5:46:26 PM` = month/day/year); `parseDate` handles them as well as ISO and `/Date(…)/`, and shows them as `03 Oct 2026, 5:46 pm` (no time when it's exactly midnight).
6. A section can instead have a fixed column order in `lib/reports/layouts.ts`. **Wallet Ledger** uses: Date & Time, Type, Narration, Amount, Cr/Dr, Closing Balance. **AEPS Reports** uses: Date & Time, Type, Aadhaar, Amount, Credited (counted as Total credit), User CB, Remarks, UTR. **PG Reports** uses: Date & Time, Customer, Card, Amount (charged to card), Charges, Credited (to bank; Total credit), Settlement, Status, Reference. **Transfer Reports** uses: Date & Time, Txn ID, Sender, Beneficiary, Account / IFSC (IFSC on a second line via the slot's `sub`; two separate CSV columns), Amount, UTR, Status, Remarks. A slot's `format: "code"` sets IDs and numbers in monospace and never breaks them across lines; `format: "words"` wraps names and remarks only between words. When a report has a Status column, summary totals count only SUCCESS rows (failed/pending/refunded moved no money). Tables must not scroll sideways: in the table, dates stack (date over time), text wraps (max two lines), long IDs use small monospace, and a slot can set `hideBelow: "lg" | "xl" | "2xl"` to drop a less important column on narrower screens (PG hides Charges below lg and Settlement/Reference below xl; AEPS hides Aadhaar below lg and User CB/UTR below xl; Transfer hides Txn ID below lg, Account / IFSC and UTR below xl, and Sender/Remarks below 2xl). Hidden columns stay in the mobile cards, search and CSV export. Each slot lists the vendor field names it accepts; Cr/Dr is also recognised by its values; when the vendor sends a date-only field plus a second date-time (or time) field, the Date & Time cell shows the complete value once (`dateCellText` in `lib/reports/table.ts`); separate credit/debit amount fields become one Amount; Amount is coloured per row by Cr/Dr. If fewer than 3 slots match, every field is shown instead. In development the server logs each report's field names (`AEPS <endpoint> fields: …`, names only) to help adjust the patterns.
7. **Export CSV** (`toCsv` in `lib/reports/table.ts`) writes the layout's columns for the rows of the current tab and search (every page, not just the one on screen; the file name includes the tab, e.g. `transfer_refundable_…csv`) in a form Excel opens correctly: a UTF-8 byte order mark (added in `ReportView`; without it `•` and `₹` are garbled), CRLF line endings, dates as `yyyy-MM-dd HH:mm` (real, sortable Excel dates), amounts exactly as the vendor sent them minus thousands separators (plain numbers Excel can sum, never rounded; the dashboard's totals skip non-SUCCESS rows and split Cr/Dr, so reproduce them in Excel with SUMIF), and digit-only IDs of 12+ digits or with a leading zero (PG reference, UTR) as `="…"` so Excel keeps them as text instead of `6.10261E+20` with the digits after the 15th lost. Text starting with `=`, `+`, `-` or `@` gets a leading `'` so vendor data (customer names, remarks) can't run as a formula (CSV injection).

**Transfer row actions.** None of these reload the whole report:
- **Refresh** (`RefreshUtrButton`; currently switched off via `ROW_REFRESH_ENABLED = false` in `ReportView`): shown in place of the UTR value when `isRefreshableTransfer()` is true. There's no single-transaction vendor endpoint, so `refreshRow()` in `ReportView` re-runs the date-range report and patches just that one row into `state.table.rows` (same position, not a full reload), then shows `RefreshResultDialog` with the row's latest status/UTR/beneficiary.
- **Dequeue / Enqueue / Refund** (`TransferActionButton`, one `TransferAction` each): shown next to the Status cell. Enqueue and Refund show together when `isRefundableTransfer()` is true; Dequeue shows only when `isQueuedTransfer()` is true **and** the row isn't refundable — refundable takes over Dequeue when both would otherwise apply, so a row shows either just Dequeue or both Enqueue and Refund, never all three. Any of them — only when the row has an id (`transferRowId()` — the vendor's internal id for the row, field name not fixed, same normalized-name matching as the flags above; seen as `3368814`-style short numbers). Each calls `POST /api/dashboard/transfer/<dequeue|enqueue|refund> { id }` (one-line route per action, all forwarding to `handleTransferAction()` in `lib/server/transferActionRequest.ts`: session-gated and rate-limited) → `callTransferAction()` in `lib/server/aepsActions.ts` → vendor `POST {CLIENT_API_BASE_URL}/Txn/<UpdateDequeue|UpdateEnqueue|ProcessRefund>?id=` (GET returns HTTP 405; confirmed via production logs), confirmed response `{ status: boolean, message: string, id: string }`. No password and no updated row come back, so clicking one opens `TransferActionResultDialog` immediately in a "Requesting…" state, then shows the vendor's own message/error and the id that was sent; on success it patches just that row locally (and after a Dequeue the report quietly reloads 10s later, so the vendor's Refundable state shows up; the result popup stays open and can't be dismissed during that 10s countdown) (`applyTransferActionPatch`: Dequeue → status "Dequeued" with queue flags cleared, Enqueue → "In Queue", Refund → "Refunded" with refund flags cleared), since the vendor returns no new row data; re-apply the date range to see the vendor's real state.

**Report start date.** No report shows anything dated before `REPORTS_START_DATE` (`2026-10-07`, in `lib/reports/dates.ts`), and the server enforces it twice: `validateRange` rejects a From date before it (HTTP 400, so a hand-made request can't ask for older data), and `fetchReport` drops every row the vendor returns whose date (the first `date`/`time` field that parses, compared as the vendor's own wall-clock date) is earlier — or that has no readable date at all. PG Reports starts earlier, on `2026-10-04` (`SECTION_START_DATES` / `reportStartDate(section)` in `lib/reports/dates.ts`; `validateRange`, `fetchReport` and the pickers all use the section's date). The date pickers only mirror the limit. Changing it needs a code change and a deploy.

To connect another section: add its endpoint, `params()` and any `transform()` to `REPORT_ENDPOINTS` in `lib/server/aepsReports.ts`, create `app/api/dashboard/<section>/route.ts` (one line: `return handleReportRequest(request, "<section>")`), and render `<ReportView section="<section>" />` on its page.

`FromDate`/`ToDate` are sent as `yyyy-MM-dd` (`VENDOR_DATE_FORMAT` in `lib/server/aepsReports.ts`), confirmed against the live ledger endpoints.

## Sharing a local build (Cloudflare quick tunnel)

```
npm run build && npm run start          # terminal 1 (or npm run dev)
cloudflared tunnel --url http://localhost:3000   # terminal 2
```

`allowedDevOrigins: ["*.trycloudflare.com"]` in `next.config.ts` lets `npm run dev` work through the tunnel. The tunnel URL is public and changes on every run; stop it when the demo ends.
